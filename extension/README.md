# Mission Desk — Muse bridge extension

A Manifest V3 extension that connects the muse.ai tab to the Mission
Desk app through the local bridge (`bridge/`, WebSocket on
127.0.0.1:7701). Design: DESIGN.md §9 (fuse B). The extension is the
only part of the system that runs inside the Muse page: its content
script probes the page's health (§6.2 checks), mirrors messages,
approvals and Activity, and performs sends by driving the page's own
controls.

**Security posture (§9, binding):**

- The bridge binds 127.0.0.1 only. Nothing here talks to any other host.
- The pairing token is generated by the bridge on first run into
  `bridge/.pairing.json` (mode 0600, gitignored). You paste it into the
  extension popup once; it is stored in `chrome.storage.local` and
  presented by the background worker in its bridge hello. It is never
  sent to any web page, never put in page storage, never logged.
- The app connects to the bridge without the token but is Origin-checked
  (local origins only). The asymmetry is deliberate: the app page's
  Origin is its identity, while the extension is a separate principal
  that an arbitrary local socket could imitate — so the extension proves
  itself with the token.
- The content script never reads, exports, or stores cookies, session
  tokens, or credentials. It reads only DOM structure and text needed to
  mirror the conversation, and its check `detail` strings contain no
  page secrets.
- Approvals are resolved by clicking the real Allow/Deny control in the
  page — never forged at the bridge or protocol level.

## Files

- `manifest.json` — MV3 manifest. Content-script matches: `https://muse.ai/*`
  plus **test-only** `http://localhost/fixture*` / `http://127.0.0.1/fixture*`
  (the fixture page in `tests/fixture/`). Remove the localhost matches
  if you ever ship this beyond your own machine.
- `background.js` — service worker: owns the bridge WebSocket (with
  backoff reconnect), holds the pairing token, routes app commands to
  the registered Muse tab. Note the MV3 caveat in its header: service
  workers suspend when idle; Chrome wakes it on content-script
  messages, and the app shows STALE rather than pretending freshness.
- `content.js` — probes, message streaming, send confirmation, approval
  and Activity mirroring. All selectors come from one config object.
- `selectors.js` — THE selector strategy: role/text/structural selectors
  in fallback order; generated class names are never primary.
- `popup.html` / `popup.js` — pairing-token entry + connection state.

## Owner real-page verification (the step only you can do)

The build was verified against a local fixture page that mimics
muse.ai's semantics (framework-controlled composer, streaming,
approvals, Activity panel). The real page's selectors are best-effort
structural guesses until this check runs once:

1. **Start the bridge:** `cd bridge && npm install && npm start`.
   On first run it writes the pairing token to `bridge/.pairing.json`
   and prints that path (not the token).
2. **Install the extension:** open `chrome://extensions`, enable
   Developer mode, "Load unpacked", choose this `extension/` folder.
3. **Pair it:** click the extension's toolbar button and paste the
   token from `bridge/.pairing.json`. The popup should say
   "Bridge: connected" once the background worker connects.
4. **Open Muse:** open https://muse.ai in a tab, signed in. (The tab
   registers itself with the extension when the content script loads.)
5. **Run the app:** from the repo root, `npm run build && npx vite preview`,
   then open **http://localhost:4173/?adapter=muse**.
6. **What to expect:** the lamp cluster (top right) walks
   connecting → ready, showing "Muse AI adapter · ready" and 11/11.
   Open the popover: the checklist should show Bridge reachable,
   Extension connected, Muse tab found, Muse page ready, Signed in,
   Composer found, Message list found, Reply observer armed, plus the
   optional Approval observer, Activity observer and Activity panel
   observer. Your agent name should appear as the identity.
7. **If a check fails on the real page:** the failing check names what
   the content script could not find (e.g. "Composer found"). That
   means a selector in `selectors.js` needs tuning to the real page's
   structure — edit that one file (role/text/structural selectors only;
   never generated class names), then REINSTALL the extension
   (unpacked, from this folder) and reload the muse.ai tab. A bare
   reload is not enough in scripted setups: some loaders snapshot
   the folder at install time, so edits only take effect on
   reinstall. The auth check failing while you ARE signed in means
   the signed-in marker selectors need the same treatment.
8. **If checks stall at partial pass** (e.g. bridge+extension pass
   but the tab never registers): query the background worker with
   `{ type: 'md-state' }` — it reports `{ bridgeOpen, tabRegistered }`
   separately, which tells a bridge outage apart from a missed
   tab registration (fixed by reloading the muse.ai tab so the
   content script re-registers).
8. **Try the loop:** open any conversation in the app, send a message —
   it should be typed into the real page's composer by the content
   script, sent with the page's own send control, and confirmed by
   observing it land; the reply streams back into the app. Approvals
   that appear in the page appear in Needs You and resolve by clicking
   the real control; the Activity view's entries mirror into Running
   Now / Recently Finished.

## Control Panel actions — the invokeAction mapping

The Muse page has no buttons of ours, so a Control Panel surface
action (`invokeAction`) is mapped onto the chat itself: the content
script sends a structured command message through the normal,
confirmed send path —

    [Mission Desk action] Run layout review (layout-review)

— and the action's "result" is the send confirmation; the bot's reply
arrives as ordinary message events, and the app shows an ack when the
command message lands. This is deliberate: the chat remains the one
channel, the action is visible in the conversation history (nothing
happens behind the user's back), and it works with the real bot
exactly as with the fixture bot, which acks by replying.

## Chat-carried intents

A bot reply may contain fenced ` ```intent ` JSON blocks (schedule /
webview proposals). The MuseAiAdapter — not the content script —
parses them out: deltas are held back from the first fence character
so a partial block never reaches the display, the final message is
delivered clean, and each block becomes an `intent.*` event. In the
app, schedule intents arrive as *proposals* the owner accepts or
rejects (never auto-filed), and webview intents open the referenced
artifact in the viewer.

## Test harness note

Headless verification loads this extension into Chromium with
`--load-extension` (see `scripts/probe-slice3.mjs`, run under xvfb). If
a future environment refuses MV3 there, the same content script can be
injected into the fixture page via CDP with `window.__MD_TEST_HOOKS__`
set (direct-WebSocket transport) — that mode exists only for tests and
labels itself in the bridge check detail ("NOT extension-loaded").
