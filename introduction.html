Mission Desk for Muse

The desk for serious Muse work. If you run Muse across several projects at once — code, a book, a research programme — Mission Desk lets you conduct all of it from one board: what's running, what needs you, what's next, with every conversation kept under its project and filed your way. This page is the whole manual: who it's for, how to install it, and how to run it.

Ready 11/11 against the real muse.ai Local-first · runs on your machine No account, no cloud, no telemetry

Made for people who run Muse like a studio

You hand Muse real projects, and you run them in parallel. At any given moment a few of your chats are mid-task, one is waiting on a decision from you, and one finished an hour ago while you were looking elsewhere. Mission Desk is where you conduct that: a board that shows the whole studio at a glance, and a filing system that works the way you think — by project.

It works with the agent, not instead of it. Everything Muse is good at stays in Muse — its memory, its search, its scheduling, its connectors, the artifacts it builds — and Mission Desk brings all of it into one view. What the desk adds is the layer that's about you: your projects and their statuses, your filing, your call on every proposal. You file, tag, rename, pin and set status yourself, by direct manipulation; when the agent suggests a filing or a better title, it arrives as a proposal you accept or reject. The organisation is yours — the agent works within it.

The multi-project builder

Several codebases on the go at once, each with its own chats, branches and review queue. You want every project's state — including what's built and waiting on your word to push — visible without opening five threads to check.

The long-haul maker

A book, a course, a research programme — work measured in chapters and months, not messages. You want the project to hold its shape: drafts as artifacts, sessions as tasks, the plan where you can see it.

The parallel operator

Three chats running is a normal afternoon. You switch between them, steer the one that's stuck, and want a finished job to announce itself — a badge, an entry in Needs You — instead of being something you discover by polling every thread.

How the pieces fit

Three parts, all on your machine. The app never touches the muse.ai page directly — two browser tabs can't talk across origins, so a small local bridge relays between them, and a browser extension is the app's eyes and hands inside the tab you already have open.

Your browser · Tab 1
muse.ai

You open it and sign in, as always. Our extension's content script rides inside it — observing and operating the page, drawing nothing on it.

Just want to look?

The app runs against a simulated adapter with zero setup — the full Mission Desk experience, with a mock agent behind it. From the repo root:

npm install
npm run dev

Open the local address it prints. Everything on the board works; only the agent is simulated. The rest of this guide is about connecting the real one.

Before you start

  • Node 20+ and Chrome (or Chromium) with the ability to enable Developer mode for extensions.
  • A muse.ai account you can sign in to — you sign in yourself, in your own browser. Nothing in this stack ever sees your password.
  • The repo cloned locally: git clone https://github.com/noctivagous/ai-bot-app.git

Tick the steps off as you go — the ticks are remembered on this machine.

1

Install dependencies

cd ai-bot-app
npm install
cd bridge && npm install && cd ..
2

Start the bridge

cd bridge && npm start

Leave it running. On first run it creates its pairing token at bridge/.pairing.json — it prints the path, never the token. You'll need that file in step 4.

3

Load the extension

Open chrome://extensions, turn on Developer mode (top right), click Load unpacked, and select the repo's extension/ folder.

4

Pair the extension with the bridge

Click the extension's toolbar icon and paste the token from bridge/.pairing.json. The popup should say “Bridge: connected”. The token lives only in that file and in the extension's own storage — never in the page, never in the repo.

5

Open muse.ai

Open muse.ai in a tab and sign in normally. The tab registers itself with the extension automatically — there's nothing to click in the page.

6

Run the app

npm run build && npx vite preview

Open http://localhost:4173/?adapter=muse. The status lamp (top right) should walk connecting → ready, and the connection popover should show 11/11 checks with your agent's name as the identity.

That's the whole install. From here you use the app in Tab 2 and keep the muse.ai tab open beside it. If step 6 doesn't reach 11/11, the failing check is the diagnosis — see The 11 checks.

The Board is home

Mission Desk is board-first; chat is a focus panel that slides over the board when you open a conversation, and slides away when you're done. The board answers three questions without opening a single chat:

  • Needs You — approvals waiting (with their once/always scope) and work that finished while you weren't looking.
  • Running Now — live job cards for conversations doing work right now; expand one to see what it's doing in detail.
  • Projects at a Glance + Coming Up — every project's state (with n running · m waiting on you rollups) and the schedule ahead. Finished work collects in Recently Finished.

You can run several chats at once — sending in one never blocks the others, and a chat finishing is an event: a badge, a Needs You entry, a toast. Not a surprise you find later.

Conversations, filed by you

The Conversations view is an editable table, not a scrollback. Inline-rename a chat (the title is yours — the agent may propose a better one, with Accept / Reject), pick its project from the row, add tags, set its status. New chats land in the Inbox tray until you file them. Projects carry a status (active · awaiting-owner · blocked · parked · done) and a kind (software, book, research, general) — software projects also show repo state, including what's awaiting a push.

Day-to-day moves

You want to…Do this
Send work to the agentOpen the conversation, type in the slide-over composer, send. The extension types it into the real muse.ai composer and confirms by watching your message land — an unconfirmed send is reported as failed, never as sent.
Approve somethingNeeds You → Allow once / Always allow / Deny. The decision is carried back and the page's real control is clicked; the decision log records the scope you chose.
Accept a schedule proposalWhen a chat proposes a session, it appears under Proposed by chat on the Schedule view. Accept files it; Reject discards it. Nothing is ever auto-filed.
Run a dashboard actionThe Control Panel (on the Board) holds action buttons — forms and commands the chat can also drive. With the Muse adapter, an action is sent as a structured chat message through the same confirmed send path.
Find an artifactThe Artifacts view lists what the agent produced with its provenance — bot · chat · project · goal — and opens it in a viewer.
Connect a resourceGlobal resources (monitor modules, email accounts, databases) live in the Control Panel's registry. Toggle which bot each connects to; the toggles persist. Data flows for monitors are a later slice — the registry says so up front.

Closing the Muse tab

The app knows whether the tab is really there. The extension heartbeats to the bridge every couple of seconds; close the tab (or navigate it away) and the app drops out of ready within moments: the tab-dependent checks fail with “Muse tab closed or not responding — reopen muse.ai”, the composer refuses to send, and — importantly — your draft is kept. Reopen muse.ai and the app returns to ready on its own. No reconnect ritual.

Eleven checks, one derived status

The connection popover (click the lamp, top right) shows a checklist. The overall phase — connecting, ready, degraded, error — is derived from these checks and nothing else, so the status can never claim more than the evidence. Reading a failure: a red check names the exact thing that wasn't found — that name is the diagnosis and, on the real page, usually the one selector to tune. See Troubleshooting.

When something's off

SymptomLikely cause & fix
A check fails on the real page (composer, message list, signed-in…) muse.ai changed its page structure; one selector needs tuning. Edit only extension/selectors.js — every lookup lives there, role/text/structural only, never generated class names — then reinstall the extension unpacked and reload the muse.ai tab. (A bare reload isn't always enough: some loaders snapshot the extension folder at install time.)
Stuck part-way: bridge + extension pass, tab never registers Ask the background worker for its state with an md-state message — it reports bridge connection and tab registration separately, which tells a bridge outage apart from a missed registration. A missed registration is fixed by reloading the muse.ai tab so the content script re-registers.
App says the tab is gone, but it's open Heartbeats were delayed — a suspended background worker, or a hidden tab whose timers Chrome throttled. Any message from the tab revives presence; reload the tab or the extension. If it flaps repeatedly on a hidden tab, that's the known throttling behaviour, not data loss.
Sends fail with “not ready” The app only sends from ready. Check the popover: the red check says why (usually the tab, or sign-in). Your draft is preserved either way — fix the cause and send again.
“Signed in” check fails while you ARE signed in The signed-in marker selectors need the same tuning treatment as any other check — see the first row.
Port 4173 behaves strangely A stale preview server from an earlier session may be squatting on the port. Kill it and restart the preview with npx vite preview --port 4173 --strictPort so it fails loudly instead of drifting to another port.
Approvals behave unverified Where this stands: the approval path is fully proven against the test fixture, and its selectors were fitted by construction, but at the time of writing no genuine approval request had yet occurred during a real-page session to exercise it end-to-end. The first real one is the test — if Needs You and the page disagree, trust the page and report the check state.

What “verified” means here

The whole fuse — extension, bridge, app — is driven end-to-end by automated probes against a local fixture page that mimics muse.ai's mechanics faithfully (its composer even rejects naive programmatic typing, the way the real one does). On top of that, the extension was calibrated against the real muse.ai: selectors fitted to the real DOM, sends confirmed by observation, replies streamed and settled to exactly one final each, tab-close detection proven. The calibration survey and report live in the repo at docs/survey/muse-ai-dom-survey.md and docs/CALIBRATION-REPORT.md.

The ground rules the stack is built on

  • Your session stays yours. The extension never reads cookies, tokens, passwords, or any credential. It observes and operates page DOM in a tab you opened and signed into. If anything ever seems to require your session material, the correct behaviour is to stop — that's a design rule, not a limitation.
  • Everything is local. The bridge binds 127.0.0.1 only. The pairing token exists only in bridge/.pairing.json and the extension's storage. Records live on your machine, hosted by the bridge.
  • Brittle, and plain about it. This fuse is unsupported by design — muse.ai can change under it. When it does, a named check fails and tells you what wasn't found, instead of the app quietly misbehaving. A status is only ever as good as its freshest evidence: checks go stale, presence times out, and the app says so.
  • Manual-first, always. The agent proposes; you dispose. Filings, retitles, status changes and schedule entries from the chat are proposals until you accept them.
  • Activity is transient. Live activity mirrors onto the board and is never written into records. What's a record is decisions and organisation — what's a stream stays a stream.
